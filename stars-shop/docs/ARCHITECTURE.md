# Архитектура

```
                Telegram                         Администратор
   ┌──────────────┬──────────────┐                  │ браузер / Mini App
   │  Bot API     │  Mini App    │                  │
   ▼              ▼ (HTTPS)      │                  ▼
┌──────┐   ┌───────────────────────────────────────────────┐
│ bot  │   │ web: nginx — TLS, статика webapp и admin,     │
│aiogram│◄──│ /api → api, /tg/webhook → bot, лимиты, CSP    │
└──┬───┘   └───────────────┬───────────────────────────────┘
   │                       ▼
   │              ┌─────────────────┐      ┌───────────────┐
   │              │ api (FastAPI)   │◄────►│ платёжные     │ вебхуки
   │              │ публичный + админ│      │ провайдеры    │
   │              └───────┬─────────┘      └───────────────┘
   │                      │
   ▼                      ▼
┌─────────────────────────────────┐    ┌──────────────────────────┐
│ PostgreSQL: заказы, платежи,    │◄──►│ worker: доставка, outbox- │──► поставщик Stars
│ события, outbox, аудит, контент │    │ уведомления, сверка,      │──► Bot API (уведомления)
└─────────────────────────────────┘    │ возвраты, истечение       │
        ▲                              └──────────────────────────┘
        │ Redis: лимиты запросов, FSM бота
```

Один Python-пакет `starshop` даёт три процесса из одного образа: `api`, `worker` и `bot`. Все работают с одной БД и одними доменными сервисами. На Vercel (`starshop/serverless.py`, [VERCEL.md](VERCEL.md)) все три работают в одной функции API. Фоновые задачи там выполняются после ответов на запросы, бот получает обновления через вебхук.

## Конечный автомат заказа

```
created ──► pending_payment ──► paid ──► processing ──► completed
   │              │              │            │              │
   ▼              ▼              ▼            ▼              ▼
cancelled ◄───────┘        refund_pending ◄─ failed    refund_pending (только владелец)
   │                             │
   └──► paid (поздняя оплата,    ▼
        подтверждённая провайдером)  refunded
```

Переходы проверяет `services/state_machine.transition()`. Он же ставит отметки времени и пишет `OrderEvent`; других путей изменить `orders.status` нет. Статус `cancelled` (не оплачен) дополняет список из ТЗ: без него нельзя отличить неоплаченный заказ от возврата.

Заказ Lucky Buy (`orders.kind = 'lucky'`) разыгрывается в той же транзакции, которая делает его `paid`. Выигрыш идёт дальше как обычная покупка. Проигрыш закрывает заказ статусом `lost`; переход `lost → refund_pending` нужен только для исключительного возврата владельцем. Механика и проверка честности описаны в [LUCKY_BUY.md](LUCKY_BUY.md).

## Сквозной сценарий

1. Mini App: `GET /bootstrap` возвращает каталог, контент, способы оплаты; `GET /me` создаёт пользователя и привязывает реферала.
2. `POST /orders/quote` — цена считается на сервере (промокод, бонусы, комиссия).
3. `POST /orders` с `Idempotency-Key` создаёт заказ `created`, резервирует промокод и списывает бонусы.
4. `POST /orders/{id}/payment` — счёт у провайдера, заказ переходит в `pending_payment`, в outbox попадает уведомление «Ожидается оплата».
5. Вебхук провайдера проходит проверку подписи, дедупликацию и сверку суммы. Заказ становится `paid`, создаётся задача доставки и уведомление «Оплата подтверждена».
6. Воркер: `processing` → вызов способа доставки → `completed` и уведомление «Stars доставлены» (или `failed`, «Нужен оператор», повтор).
7. Mini App опрашивает заказ каждые 4 секунды, пока статус активный, и показывает ленту событий.

## Данные

* Деньги — `NUMERIC(14,2)`, цены за звезду — `NUMERIC(14,4)`, расчёты в `Decimal`. В JSON суммы передаются строками.
* Время хранится в `timestamptz` (UTC). Бот и CSV показывают его в `DISPLAY_TIMEZONE`, Mini App — в часовом поясе магазина.
* Ограничения на уровне БД: формула `total = subtotal − discount − bonus + fee`, неотрицательный бонусный баланс, один успешный платёж на заказ, один «популярный» пакет, одна задача доставки на заказ, уникальные ключи идемпотентности.
* Изменяемые настройки и контент лежат в `app_settings` (JSON по ключам, проверяются pydantic-моделями со значениями по умолчанию). Секретов там нет.

## Почему без Celery

Очередь доставки и уведомлений построена на PostgreSQL: задачи создаются в той же транзакции, что и изменение заказа (transactional outbox), а забираются через `SKIP LOCKED`. Поэтому не бывает ни «оплачено, но задачи нет», ни «уведомление ушло, а заказ откатился». Redis используется только там, где он действительно нужен: общие лимиты запросов для нескольких процессов API и состояния диалогов бота.
