# Платежи

## Прежде чем принимать реальные деньги

Магазин продаёт **цифровой товар внутри Telegram**, поэтому перед запуском проверьте правила по первоисточникам. Во время разработки они не перепроверялись онлайн, а меняются они регулярно:

* [Условия для разработчиков ботов](https://telegram.org/tos/bot-developers) и [Bot Payments API for Digital Goods](https://core.telegram.org/bots/payments-stars). По известным нам правилам цифровые товары и услуги внутри ботов и Mini Apps продаются за Telegram Stars (`XTR`). Оплачивать звёзды звёздами бессмысленно, поэтому у магазина Stars внешняя оплата. Её допустимость для вашей схемы продаж и платформ (iOS/Android/Desktop) нужно подтвердить отдельно.
* [Правила оформления Telegram Mini Apps](https://core.telegram.org/bots/webapps) и [Условия Telegram Stars](https://telegram.org/tos/stars).
* Правила выбранного платёжного провайдера: разрешена ли продажа цифровых активов, требования KYC/AML, страны покупателей.
* Законодательство вашей страны: приём платежей, налоги, оферта, защита прав потребителей.

Официально Telegram продаёт Stars через встроенные покупки в приложениях, @PremiumBot и [Fragment](https://fragment.com). Проект **не утверждает**, что какой-либо из подключённых способов оплаты подходит для вашей схемы без такой проверки. Production-режим по умолчанию выключен (`ALLOW_PRODUCTION=false`).

## Как устроен модуль

```
starshop/payments/
  base.py       интерфейс PaymentProvider
  demo.py       DEMO-провайдер (только в DEMO-режиме)
  cryptopay.py  Crypto Pay API (@CryptoBot)
  registry.py   выбор провайдеров по PAYMENT_PROVIDERS
  service.py    создание платежей, вебхуки, сверка, возвраты
```

Метод `PaymentProvider`:

| Метод | Назначение |
| --- | --- |
| `create_payment(payment, ctx)` | создать счёт у провайдера → `PaymentIntent` (ссылка и её тип: `telegram` / `external` / `internal`) |
| `parse_webhook(headers, body)` | **проверить подпись** (при ошибке исключение `WebhookSignatureError`) и разобрать событие |
| `fetch_state(payment)` | запрос статуса у провайдера (сервер–сервер) |
| `refund(payment, order, user)` | возврат; при сбое `PaymentProviderError(retryable=…)` |
| `cancel(payment)` | аннулировать неоплаченный счёт (best effort) |
| `balances()` | денежный остаток у провайдера для дашборда (если API это позволяет) |

## Гарантии

* **Заказ считается оплаченным только по данным провайдера.** Это либо событие с проверенной подписью, либо прямой запрос статуса с сервера. Возврат пользователя на страницу, параметры вроде `success=true` и нажатие «Я оплатил» платёж не подтверждают: кнопка только просит сервер спросить провайдера.
* **Проверка суммы, валюты и ссылки.** Сумма и валюта от провайдера должны совпадать с платежом, а `payload`/`reference` — с нашим `payment.id`. При расхождении заказ не оплачивается, админы получают уведомление.
* **Без повторной обработки.** Таблица `payment_webhook_events` имеет уникальный ключ `(provider, event_id)`. Запись события и все изменения заказа идут в одной транзакции. Если обработка падает, транзакция откатывается целиком, и повтор от провайдера обработается нормально. Запросы с неверной подписью пишутся в журнал без `event_id` и не могут «занять» номер настоящего события.
* **Идемпотентность.** Заказы создаются по заголовку `Idempotency-Key`; открытый счёт того же провайдера переиспользуется. Частичный уникальный индекс не даёт двум успешным платежам на одном заказе.
* **Повторная оплата.** Второй успешный платёж по уже оплаченному заказу не засчитывается: он получает флаг «дубль», уходит в `refund_pending`, и воркер возвращает деньги автоматически.
* **Поздняя оплата.** Если провайдер подтвердил оплату после того, как заказ отменился по таймауту, заказ восстанавливается в `paid` (событие `late_payment`).
* **Сверка.** Воркер каждые 30 секунд опрашивает провайдера по ожидающим платежам (на случай потерянного вебхука). Перед отменой просроченного заказа он проверяет оплату в последний раз.
* **Возвраты** выполняются воркером асинхронно с экспоненциальной паузой между попытками. Если провайдер не смог вернуть деньги, админы получают уведомление. Владелец может подтвердить ручной возврат, указав номер операции (действие пишется в журнал). Пометить неоплаченный заказ оплаченным вручную нельзя: такого действия нет ни в API, ни в интерфейсе.

## DEMO-провайдер

Работает только в DEMO-режиме. Страница `/pay/demo/<id>` в Mini App явно помечена как DEMO. Кнопки на ней вызывают backend, который формирует **подписанное HMAC событие** и прогоняет его через тот же конвейер, что и у реального провайдера: подпись, дедупликация, проверка суммы.

## Crypto Pay (@CryptoBot)

1. Создайте приложение: @CryptoBot (или @CryptoTestnetBot для тестов) → *Crypto Pay* → *Create App* → скопируйте токен.
2. В приложении включите **Webhooks** с URL `https://DOMAIN/api/v1/webhooks/payments/cryptopay`.
3. Для автоматических возвратов включите в приложении переводы (*Transfers*): возврат отправляется на кошелёк @CryptoBot покупателя методом `transfer` с уникальным `spend_id`, поэтому повтор не приводит к двойному возврату.
4. В `.env`:

```env
PAYMENT_PROVIDERS=cryptopay        # demo,cryptopay — оба в DEMO-режиме
CRYPTOPAY_API_TOKEN=...
CRYPTOPAY_NETWORK=testnet          # mainnet — только после теста
CRYPTOPAY_ACCEPTED_ASSETS=USDT,TON,BTC
```

Счета выставляются в валюте магазина (`currency_type=fiat`, `fiat=SHOP_CURRENCY`); покупатель платит криптовалютой по курсу Crypto Pay внутри Telegram. Подпись вебхука проверяется по заголовку `crypto-pay-api-signature` (HMAC-SHA256 тела, ключ — SHA256 от токена). После этого счёт ещё раз запрашивается через `getInvoices` (отключается `CRYPTOPAY_VERIFY_VIA_API=false`).

Адаптер проверен на моках API (`tests/test_cryptopay.py`), но **не проверялся на реальном Crypto Pay**: в окружении разработки не было ключей. Перед production проведите полную покупку и возврат в testnet.

## Комиссия

В админке (*Настройки → Комиссии*) задаются процент для каждого провайдера и фиксированная сумма. Комиссия добавляется к заказу и показывается покупателю до оплаты.

## Как добавить провайдера

1. Создайте класс-наследник `PaymentProvider` в `starshop/payments/<name>.py`, проверяйте подпись в `parse_webhook`.
2. Зарегистрируйте его в `registry.py` (`KNOWN_PROVIDERS`, `_build`).
3. Добавьте настройки в `config.py` и `.env.example`.
4. Напишите тесты по образцу `tests/test_cryptopay.py`: подпись, повторный вебхук, расхождение суммы, сбой API, возврат.
