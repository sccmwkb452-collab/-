# Доставка Stars

Доставка — это фактическое зачисление Telegram Stars получателю. Магазин нигде её **не имитирует**: уведомление «Stars доставлены» создаётся в той же транзакции, что и перевод заказа в `completed`, а сам перевод происходит только по подтверждению способа доставки.

Способ задаётся переменной `DELIVERY_PROVIDER`.

| Значение | Когда использовать | Что происходит |
| --- | --- | --- |
| `demo` | разработка, демонстрация | Stars **не отправляются**, заказ отмечается «DEMO: заказ выполнен без отправки Stars». Работает только для DEMO-заказов |
| `manual` | старт продаж без интеграций | Задача получает статус «Нужен оператор», админам приходит уведомление. Оператор покупает Stars на [fragment.com](https://fragment.com) для `@username` получателя и нажимает в админке «Подтвердить доставку», указывая хэш транзакции. Только после этого заказ выполнен и покупатель уведомлён |
| `http_supplier` | автоматизация через поставщика | REST-контракт ниже. Поставщика или мост к нему вы подключаете сами |

Fragment — официальная площадка Telegram для покупки Stars (оплата в TON). Публичного API у неё нет, поэтому автоматизация возможна только через внешнего поставщика или собственный сервис, реализующий контракт ниже. Убедитесь, что выбранная схема соответствует правилам Telegram и Fragment.

Ограничения размера заказа (`DELIVERY_MIN_STARS`, по умолчанию 50, и `DELIVERY_MAX_STARS`) применяются ко всем пакетам и к вводу произвольного количества.

## Надёжность и повторы

* Задача доставки создаётся в той же транзакции, что и подтверждение оплаты: одна задача на заказ (уникальный `order_id`).
* Воркер забирает задачи через `FOR UPDATE SKIP LOCKED`, поэтому несколько воркеров работают безопасно. Внешний вызов делается без удержания блокировок.
* Каждый запрос к поставщику несёт один и тот же `Idempotency-Key = dlv-<order_id>`.
* Как обрабатываются ошибки:
  * сбой, при котором запрос точно не выполнен (соединение отклонено): повтор с паузой 30 с → 1 ч;
  * неясный результат (тайм-аут): повтор, только если поставщик дедуплицирует запросы (`idempotent=True`); иначе задача уходит оператору;
  * отказ поставщика: заказ `failed`, покупатель получает «Возникла проблема», админы — уведомление; дальше повтор или возврат;
  * превышен лимит попыток (`DELIVERY_MAX_ATTEMPTS`): `failed`.
* Если воркер упал посреди вызова, через 10 минут задача либо возвращается в очередь (поставщик с идемпотентностью), либо уходит оператору.
* Повтор из админки для поставщика без защиты от дублей требует подтверждения «Stars не были доставлены».

## Контракт HTTP-поставщика (`http_supplier`)

```env
DELIVERY_PROVIDER=http_supplier
SUPPLIER_API_URL=https://supplier.example.com
SUPPLIER_API_KEY=...       # Authorization: Bearer
SUPPLIER_API_SECRET=...    # подпись запросов и колбэков
```

**Подпись** (в обе стороны):

```
X-Timestamp: <unix seconds>
X-Signature: hex(HMAC_SHA256(SUPPLIER_API_SECRET, "<timestamp>.<raw body>"))
```

Колбэки старше 5 минут отклоняются.

### `POST /v1/deliveries`

Заголовки: `Authorization`, `Idempotency-Key`, `X-Timestamp`, `X-Signature`.

```json
{
  "idempotency_key": "dlv-6f1c…",
  "reference": "7KQ2M9XD",
  "stars": 500,
  "recipient": { "username": "durov", "telegram_id": null },
  "callback_url": "https://DOMAIN/api/v1/webhooks/delivery/http_supplier"
}
```

Ответ `200/201`:

```json
{ "id": "sup-123", "status": "processing" }
```

`status`: `completed` | `processing` (или `accepted`, `pending`) | `failed` (или `rejected`); необязательные поля `error`, `tx_id`, `completed_at`.

Поставщик **обязан** вернуть ту же доставку на повторный запрос с тем же `Idempotency-Key`, а не создавать новую.

Как трактуются коды ответа: `4xx` — окончательный отказ (Stars точно не отправлены); `429` и `5xx` — временная ошибка.

### `GET /v1/deliveries/{id}`

Возвращает тот же объект. Пока доставка в статусе `processing`, воркер опрашивает этот метод каждые 30 секунд.

### `GET /v1/recipients/{username}` (необязательно)

`200 {"found": true, "name": "Pavel"}` | `404` — получатель не найден. Если метод не реализован (`405/501`), проверка пропускается. Вызывается при вводе получателя в Mini App.

### Колбэк поставщика → магазин

`POST https://DOMAIN/api/v1/webhooks/delivery/http_supplier` с телом как в ответе `GET` и подписью. Повторные колбэки безопасны: финальный статус не перезаписывается.

Пример полного цикла — тест `test_http_supplier_contract` в `backend/tests/test_delivery.py`.


## Telegram Premium

Premium-заказы идут через `PREMIUM_DELIVERY_PROVIDER` (пусто — тот же канал, что и Stars):

| Значение | Как работает |
| --- | --- |
| `demo` | Только DEMO, ничего не подключается |
| `manual` | Оператор дарит Premium на fragment.com и подтверждает доставку в админке |
| `http_supplier` | Тот же контракт поставщика, в теле `"product": "premium", "months": 3/6/12`, `stars` = 0 |
| `telegram_premium` | Бот дарит Premium методом Bot API `giftPremiumSubscription` со своего баланса звёзд: 1000 ⭐ за 3 мес., 1500 за 6, 2500 за 12. Получатель должен быть пользователем магазина (бот знает его Telegram ID). При нехватке звёзд на балансе бота заказ уходит оператору. DEMO-заказы этим способом не выполняются |

## Вывод бонусов

Одобренная заявка на вывод создаёт обычный заказ Stars (`kind = withdrawal`, оплачен бонусами, `total = 0`) на аккаунт пользователя и проходит через `DELIVERY_PROVIDER`.
